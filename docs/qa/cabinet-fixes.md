   Сделать: перед каждой записью перечитывать localStorage и сливать по id — запись с более поздним updatedAt побеждает
   (у заказов updatedAt ставить при каждом изменении во всех местах: AdminOrdersPage, OrderDetailPage, PaymentPage,
   NewOrderPage; у документов/решений — своё поле времени); массивы в памяти после записи обновлять на слитые (мутируя
   тот же массив, на него ссылаются компоненты). Слушать событие `storage` — обновлять массивы в памяти и сообщать
   интерфейсу (например, своё событие `techagent:data`, на которое подписаны DashboardLayout, AdminLayout, PaymentPage
   и т. п. для перерисовки). Счётчик номеров заказов тоже перечитывать перед выдачей номера, чтобы две вкладки не дали
   одинаковых номеров.

2. **Боевая сборка без бэкенда — честно обозначить.** В режиме НЕ DEMO_MODE показать тонкую плашку на /register, /login

3. **Отрицательная сумма «к выплате»** (partnerDocuments.ts ~189, вывод ~246 и ~281). Считать так:
   - долг по удержаниям = сумма вознаграждений всех заказов Партнёра, которые возвращены после выдачи (returnedAt) и уже
     вошли в какой-либо отчёт агента, минус всё, что уже удержано в прежних отчётах (хранить в документе
     `deductedAmount`, плюс `deductedOrderIds` — по каким заказам удержание впервые показано);
   - удержать в этом отчёте = min(долг, начислено за период); к выплате = начислено − удержано (не меньше 0);
   - в тексте отчёта: блок «УДЕРЖАНИЕ ПО ВОЗВРАТАМ (п. 7.3)» — строки по новым возвратам («Заказ #…: Товар возвращён
     Покупателем …, вознаграждение по отчёту за … удерживается: −… ₽»), строка «Остаток удержания с прошлых периодов:
     −… ₽» (если есть), «Удержано в этом периоде: −… ₽», «Переносится на следующие периоды: … ₽» (если > 0), затем
     пустая строка и «Вознаграждение Партнёра к выплате: … ₽»; в акте — «Вознаграждение Агента: …», «Удержано по
     возвратам (п. 7.3 агентского договора-оферты): −…», «К выплате: …». Минус везде один и тот же знак «−».
   - отчёт формируется, только если за период есть выданные заказы (иначе удерживать не из чего — удержание ждёт).

4. **Отмена с возвратом для «В пути» и «Прибыл в пункт выдачи»** (AdminOrdersPage.tsx ~160: refundable). Разрешить для

6. **Проверки полей** — один общий модуль (например src/utils/validate.ts), одинаково в регистрации и профиле:
   - ИНН: 10 цифр (юрлицо) или 12 (предприниматель) с контрольной суммой;
   - ОГРН 13 цифр / ОГРНИП 15 с контрольной цифрой; длина согласована с ИНН (10↔13, 12↔15);
   - БИК: 9 цифр, начинается с «04»;
   - расчётный счёт: 20 цифр, контрольный ключ по БИК (стандартный алгоритм ЦБ);
   - телефон: российский номер, 11 цифр с 7 или 8 (или 10 цифр), показывать в виде +7 900 000-00-00;
   - email — нормальная проверка формата.
   В профиле — нельзя сохранить пустые обязательные поля и неверные значения, у подтверждённого партнёра нельзя стереть
   телефон. В новом заказе — телефон и email покупателя по тем же правилам (email необязателен).
